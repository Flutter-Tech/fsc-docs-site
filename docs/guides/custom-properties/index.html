Adding custom properties to your repository

Learn how to add custom properties metadata to your repositories using CBG

This public content is an excerpt from Flutter staff GitHub docs. It is published as a reference to show how GitHub is used for inner source at Flutter.

The Codebase Governor (CBG) now supports custom properties, a powerful feature that enables capability owners to add metadata tags to their repositories for enhanced organization, filtering, and data insights. This feature provides a standardized way to classify and categorize repositories across your capabilities.

What are Custom Properties?

Custom properties are metadata tags that can be applied to GitHub repositories to provide additional context and enable better organization. These properties serve as standardized labels that help teams categorize, filter, and analyze their repositories more effectively.

In CBG, custom properties are defined at the organization level by the Alpha-ops team and can be applied to repositories through your YAML configuration files in the org-config repository. Once applied, these properties appear in the GitHub repository interface and can be used for filtering and reporting purposes.

How Custom Properties Work in CBG

Custom properties in CBG follow a two-level configuration approach:

Organization-Level Definition

Custom properties must first be created at the GitHub organization level by the Alpha-ops team. This ensures consistency and prevents naming conflicts across the organization. Property types include:

  • Single-select: Choose one value from a predefined list
  • Multi-select: Choose multiple values from a predefined list
  • Boolean: True/false values
  • Text: Free-form text input

Capability-Level Configuration

Once properties are defined at the organization level, capability owners can assign values to these properties through their CBG YAML configuration files in the org-config repository.

Configuring Custom Properties

Custom properties can be configured at two levels in your CBG YAML files within the org-config repository:

Capability Defaults

Define default custom property values for all repositories in a capability using the _defaults.yml file:

defaults:
  custom-properties:
    property-name: "value"

Repository-Specific Overrides

Repository-level custom properties can be configured in individual repository configuration files to override capability defaults.

Important: Repository-level custom properties completely override capability defaults - there is no inheritance or merging. If a repository defines any custom properties, it must explicitly include all desired properties.

Example Override Behavior:

# _defaults.yml has: property-a, property-b, property-c
# Repository config:
custom-properties:
  property-a: "new-value"    # Override default
  property-d: "additional"   # Add new property
# Result: Repository gets ONLY property-a and property-d
# property-b and property-c from defaults are NOT inherited

Available Custom Properties

Capability Property (Automatically Managed)

The capability custom property is automatically managed by CBG and does not need to be defined in your YAML configuration files. This property is set to the name of the capability that contains the repository and helps identify which capability owns each repository.

Getting Started

To begin using custom properties in your capability:

  1. Review Available Properties: Contact the Alpha-ops team to understand which custom properties are available for use in your organization beyond the automatically managed capability property.

  2. Configure Defaults: Add appropriate custom properties to your capability’s _defaults.yml file in the org-config repository when additional properties become available.

  3. Override as Needed: For repositories that require different property values, create repository-specific configurations in the org-config repository.

  4. Test and Validate: Create a pull request with your custom property configurations in the org-config repository and review the CBG preview to ensure correct application.

Examples

Capability Defaults Example

description: >
  Capability for managing user authentication services

owner: auth-team-lead
maintainers:
  - auth-team-lead
  - senior-developer

defaults:
  custom-properties:
    # Additional properties will be configured here
    # when they become available

Repository Override Example

description: >
  Main authentication service API

custom-properties:
  # Custom property configurations will be added here
  # when additional properties become available

Note: The examples above show the structure for custom properties. Actual property names and values will be documented when additional properties beyond capability are made available.
